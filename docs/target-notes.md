## 2. Exact HTTP contracts

### Shared conventions and error-delivery caveats

Routes mount at `/`, with **no `/api` prefix**. Host bases are auth `http://localhost:3004`, product `http://localhost:3002`, and order `http://localhost:3003`. JSON bodies use `Content-Type: application/json`; product creation also supports multipart images. CORS permits `FRONTEND_URL` (default `http://localhost:3000`) with credentials. Evidence: `ecommerce-microservices/docker-compose.yml:77-86,95-106,119-128`; `ecommerce-microservices/auth-service/src/index.ts:15-26`, `ecommerce-microservices/product-service/src/index.ts:15-19`, `ecommerce-microservices/order-service/src/index.ts:15-23`.

Protected routes require `Authorization: Bearer <accessToken>`. Missing/wrong-prefix headers return `401 {"error":"No token provided"}`; JWT verification failure returns `401 {"error":"Invalid token"}`. Admin routes additionally require JWT `role` equal to `ADMIN`, otherwise `403 {"error":"Insufficient permissions"}`. Verification uses `JWT_SECRET`; product/order trust the token's claims without querying auth's user table. Evidence: `ecommerce-microservices/auth-service/src/middlewares/auth.ts:5-35`, `ecommerce-microservices/product-service/src/middlewares/auth.ts:5-35`, `ecommerce-microservices/order-service/src/middlewares/auth.ts:5-35`.

Auth applies an IP-based limit of 100 requests per 15 minutes across its routes, with configured error body `{"error":"Too many requests, please try again later"}` (rate-limit response, conventionally 429). Auth declares an error handler mapping `AppError` to its status and `{"error":message}`, and other errors to `500 {"error":"Internal server error"}`. **However, its async controllers are passed directly to Express 4 routes without a rejection wrapper or `next(error)`**, so thrown/rejected errors are not explicitly forwarded to that handler. Below, “intended” distinguishes those thrown errors from direct `res.status(...).json(...)` responses; hanging requests/process failure must be verified, not assumed. Evidence: `ecommerce-microservices/auth-service/src/index.ts:19-28`, `ecommerce-microservices/auth-service/src/middlewares/errorHandler.ts:4-23`, `ecommerce-microservices/auth-service/src/routes/authRoutes.ts:22-28`, `ecommerce-microservices/auth-service/package.json:10`.

Product also registers async controllers directly and installs **no custom error handler**. Its route validators do not have a `validationResult` check in either controller. There is no defined JSON error contract for rejected Redis, Prisma, MongoDB or Cloudinary operations, nor a guaranteed validation 400. Order does wrap controllers with `asyncHandler(...).catch(next)` and installs a handler returning `500 {"error":"Internal server error"}` for forwarded exceptions, but its create-order validator results are also never checked. Evidence: `ecommerce-microservices/product-service/src/routes/productRoutes.ts:17-68`, `ecommerce-microservices/product-service/src/controllers/productController.ts:1-227`, `ecommerce-microservices/product-service/src/controllers/categoryController.ts:1-34`, `ecommerce-microservices/product-service/src/index.ts:19-37`; `ecommerce-microservices/order-service/src/routes/orderRoutes.ts:17-49`, `ecommerce-microservices/order-service/src/controllers/orderController.ts:15-84`, `ecommerce-microservices/order-service/src/utils/asyncHandler.ts:3-6`, `ecommerce-microservices/order-service/src/middlewares/errorHandler.ts:4-11`.

### Register — `POST /register` (auth)

Auth: public. Body: `{"name":"Load User","email":"user@example.com","password":"<at-least-6-characters>"}`; only these three fields are selected for creation. Name is trimmed and nonempty; email must pass `isEmail`; password length minimum 6. No `confirmPassword` or role field is needed/used. Success: `201 {"user":{"id":string,"name":string,"email":string,"role":"USER"},"accessToken":string,"refreshToken":string}`. Validation failure: direct `400 {"errors":[...]}`, the library's `errors.array()` entries including field error details (type/value/msg/path/location as supplied by express-validator). Auth: no access-token requirement. Body: `{"refreshToken":"<token>"}`. Success: `200 {"accessToken":string,"refreshToken":string}` (no user object). ### Create order — `POST /orders` (order)

Auth: any valid Bearer token (`USER` or `ADMIN`). JSON body:

```json
{
  "items": [
    {"productId": "<product-id>", "name": "Load Product", "price": 12.5, "quantity": 1, "image": "<optional-image-url>"}
  ],
  "shippingAddress": {"street": "1 Test Street", "city": "Test City", "state": "TS", "zip": "12345", "country": "US"},

```

Declared validators: nonempty items array; each productId/name nonempty, price float >=0, quantity int >=1; shippingAddress object and each listed address field nonempty. `paymentMethod` has no validator. **These validation results are never checked**; malformed inputs may be stored if Prisma accepts them, or fail later (e.g. absent items causes `.reduce` failure). Success: `201 {"order":Order-with-items}` for the bypass/fallback branch, or `201 {"order":Order-with-items,"clientSecret":string|null}` when Stripe creation/update/publication succeeds. Both start from a persisted pending order; creating a payment intent is not payment confirmation. On the Stripe branch the returned `order` is the pre-update object, so its `paymentIntentId` can still be null although the DB has been updated. Shared auth 401; exceptions escaping the controller (including final publish failures) produce `500 {"error":"Internal server error"}`. No effective validation 400 is implemented here. ## 3. Order creation deep dive

1. JWT authentication precedes the declared body validators, then `asyncHandler(createOrder)`. The controller does not check validation results. Evidence: `ecommerce-microservices/order-service/src/routes/orderRoutes.ts:17-34`, `ecommerce-microservices/order-service/src/controllers/orderController.ts:15-18`.
2. It computes subtotal from **client-supplied** price × quantity; shipping is 0 only if subtotal **strictly exceeds 100**, otherwise 10; total=subtotal+shipping. There is no product/auth service request, inventory check, price lookup, stock decrement or coupon calculation in this flow. Evidence: `ecommerce-microservices/order-service/src/controllers/orderController.ts:18-43`.
3. Prisma stores the order and nested items in `ecommerce_orders` before payment/publish. UserId and productId are plain strings without cross-database user/product foreign keys; the auth schema's separate `Order` model is not written by this controller. Evidence: `ecommerce-microservices/order-service/src/controllers/orderController.ts:25-43`, `ecommerce-microservices/order-service/prisma/schema.prisma:10-37`, `ecommerce-microservices/auth-service/prisma/schema.prisma:30-41`, `ecommerce-microservices/docker-compose.yml:80,122`.
4. Stripe client construction is guarded by `startsWith("sk_live") || (startsWith("sk_test_") && !includes("placeholder"))`, using JavaScript's operator precedence. A live-prefix value is not subject to the placeholder exclusion. The Compose default is a test-prefix placeholder, so **the client is null and even `paymentMethod:"stripe"` skips the remote call**. There is no failure due solely to this placeholder: with DB/broker operations successful, the fallback returns 201 with `{order}`. Evidence: `ecommerce-microservices/order-service/src/controllers/orderController.ts:10-13,45-83`, `ecommerce-microservices/docker-compose.yml:123-124`.
5. A qualifying environment key plus exact `paymentMethod:"stripe"` creates a USD PaymentIntent for `Math.round(total*100)`, metadata `{orderId}`, then stores its ID, publishes `order.created` and returns 201 with clientSecret. The entire intent/update/publish block is inside one try/catch. Any failure there is logged as `Stripe payment failed, order created without payment:` and falls through; the existing DB order is not undone. A successful intent update followed by publish failure therefore enters the same misleading log path. Evidence: `ecommerce-microservices/order-service/src/controllers/orderController.ts:45-83`.
6. The fallback publishes `order.created` and only then returns 201. Both publish sites send `{orderId:order.id,userId:req.user.id,total,items}`; items are the **original request items**, not persisted OrderItem records, and shipping address/customer email are not included. Exchange `orders` is durable topic; messages JSON-encode the payload and set `persistent:true`. `order.created` is a routing key; the consumer queue is named **`notifications`**, not `order.created`. Evidence: `ecommerce-microservices/order-service/src/controllers/orderController.ts:58-80`, `ecommerce-microservices/order-service/src/utils/rabbitmq.ts:6-29`, `ecommerce-microservices/notification-service/src/consumers/orderConsumer.ts:141-154`.

**Publish failure semantics:** `publishEvent` throws if the channel was never initialized; otherwise it calls `channel.publish` on an ordinary channel. It has no catch, retry, outbox, confirm channel, publisher acknowledgement, mandatory routing option, or handling of the publish boolean/backpressure return. A synchronous publish exception rejects `publishEvent`; on the Stripe path it is first caught, then publication is attempted again outside the catch. Failure of that final attempt produces JSON 500 through the wrapper/error handler. **The order remains created** (and the paymentIntentId may already be persisted); there is no delete/compensation. A successful return from `publishEvent` is not broker/consumer delivery confirmation. Connection error/close events are not handled in the publisher utility, so some asynchronous failures need runtime verification rather than being assumed to produce HTTP 500. Evidence: `ecommerce-microservices/order-service/src/utils/rabbitmq.ts:4-29`, `ecommerce-microservices/order-service/src/controllers/orderController.ts:25-83`, `ecommerce-microservices/order-service/src/utils/asyncHandler.ts:3-6`, `ecommerce-microservices/order-service/src/middlewares/errorHandler.ts:10-11`.

**Existing offline/bypass paths:** an unset/empty key, the Compose placeholder, or a key not matching the construction guard leaves stripe=null; `paymentMethod` omitted or any value other than exact `"stripe"` skips payment even with a client. No `MOCK_PAYMENTS`, mock Stripe implementation, or payment-disable toggle is implemented in this controller. It already has an unpaid-order path, so Phase 0 supplies no payment patch. Qualifying real/test keys enable external Stripe calls, not an offline mock. Evidence: `ecommerce-microservices/order-service/src/controllers/orderController.ts:10-13,16,45-83`, `ecommerce-microservices/docker-compose.yml:123-124`.

The Stripe webhook `POST /webhook/stripe` uses raw JSON bytes, returns 400 `Stripe not configured` with stripe=null, 400 `Invalid signature` on construction failure, and on `payment_intent.succeeded` updates status to confirmed/paidAt and publishes `payment.confirmed` with **only `{orderId}`**. Other accepted events return `{received:true}`. The frontend submits `paymentMethod:"stripe"`, clears the cart and redirects on any successful order response; it does not use clientSecret or confirm the payment. Evidence: `ecommerce-microservices/order-service/src/index.ts:18-19`, `ecommerce-microservices/order-service/src/routes/orderRoutes.ts:49`, `ecommerce-microservices/order-service/src/controllers/orderController.ts:258-292`, `ecommerce-microservices/frontend/src/app/checkout/page.tsx:49-73`.

Order-service must establish its initial AMQP connection/exchange before listening; startup connection failure logs and exits 1. No application-level startup retry or post-connection reconnect handler exists there. Compose's application restart policy may restart an exited container; this is not publisher reconnect logic. Evidence: `ecommerce-microservices/order-service/src/index.ts:25-38`, `ecommerce-microservices/order-service/src/utils/rabbitmq.ts:6-14`, `ecommerce-microservices/docker-compose.yml:129-134`.

## 4. Redis usage and unavailability

There is no `isReady` guard, command deadline, explicit reconnect strategy, offline-queue configuration, try/catch fallback, or circuit breaker in the wrapper. Evidence: `ecommerce-microservices/product-service/src/utils/cache.ts:1-28`, `ecommerce-microservices/product-service/package.json:15`.

**At startup:** MongoDB connection is awaited first, Redis connect second, then HTTP listen. Product service cannot begin listening while connectRedis is pending; a rejected connect/startup operation logs and exits 1. Compose also requires Redis healthy before initial dependency startup. The source does not establish how long node-redis will retry or remain pending under each network failure. **During requests:** cache read is awaited before the DB fallback, and cache write is awaited before success is returned. A cache miss (`null`) reaches the DB; **an unavailable Redis is not treated as a cache miss**. A rejected GET prevents DB access on that path; a pending GET stalls it. A rejected/pending SET prevents the success response even after a successful DB read. Mutations persist to PostgreSQL (and uploads may finish) before awaited cache invalidation, so a Redis problem can occur after durable changes. The console error listener does not suppress rejected commands or provide fallback. ## 5. Notification service

Startup first connects MongoDB (failure logs and exits 1), then attempts `startConsumer` at most ten times, with a fixed 5000ms wait after each of the first nine failures. Exhaustion exits 1. This is startup retry, **not continuous reconnect**: on success it returns from the startup loop. Consumer code registers no connection/channel `error` or `close` handlers and no resubscribe loop. What actually happens after an established RabbitMQ connection drops is unverified. Evidence: `ecommerce-microservices/notification-service/src/index.ts:10-40`, `ecommerce-microservices/notification-service/src/consumers/orderConsumer.ts:137-184`.

It asserts durable topic exchange `orders`, durable queue **`notifications`**, and binds `order.created`, `payment.confirmed`, `order.shipped`, `order.delivered`. There is no declared prefetch, dead-letter queue, message schema validation or deduplication. `order.confirmed` and `order.cancelled` can be published by order status updates but are not bound here. Evidence: `ecommerce-microservices/notification-service/src/consumers/orderConsumer.ts:137-181`, `ecommerce-microservices/order-service/src/controllers/orderController.ts:175-190`.

Every handler generates an HTML template and sends to the hardcoded **`customer@example.com`**, not the authenticated user's email. Created-order templates use total (fallback 0) and item names/quantities (fallback []); payment/delivery use orderId; shipping uses trackingNumber/estimatedDelivery (fallback empty strings). It then stores a MongoDB Notification with `type,email,subject,html,metadata:<event>,status:"sent"`; schema supplies identity, timestamps and supports `sent|failed`, but handlers never persist failed status. Evidence: `ecommerce-microservices/notification-service/src/consumers/orderConsumer.ts:33-135`, `ecommerce-microservices/notification-service/src/templates/emails.ts:1-89`, `ecommerce-microservices/notification-service/src/models/Notification.ts:13-28`.

Email uses Resend initialized from `RESEND_API_KEY`; sender uses `FROM_EMAIL` (default noreply@ecommerce.com). There is **no SMTP/MailHog adapter or SMTP env lookup** in the email utility; MailHog appears as infrastructure, not a notification dependency. `sendEmail` catches thrown send errors and returns false. Handlers await it but ignore the boolean and return true from their retry callback, so a caught email failure is considered successful, stored as sent, and acknowledged. The wrapper also does not inspect the resolved Resend response for an error field. Exact SDK rejection/resolution behavior for the placeholder is not determined from this application source. Evidence: `ecommerce-microservices/notification-service/src/utils/email.ts:4-23`, `ecommerce-microservices/notification-service/src/consumers/orderConsumer.ts:42-58,66-82,94-110,118-134`, `ecommerce-microservices/docker-compose.yml:66-71,136-149`, `ecommerce-microservices/notification-service/package.json:12`.

`retryWithBackoff` actually makes up to three attempts with linear waits 1000ms then 2000ms for **thrown** errors. Successful handler completion gets `ack`. Errors inside the processing try get `nack(msg,false,true)` (requeue) with no bounded delivery count. MongoDB save failure after an email attempt can therefore lead to repeated email attempts on redelivery. `JSON.parse` occurs **before** the processing try, so malformed JSON is not covered by this nack path. The `channel.consume` promise is also not awaited before logging startup completion. Evidence: `ecommerce-microservices/notification-service/src/consumers/orderConsumer.ts:16-31,42-58,163-184`.

## 6. Seeding and admin role

There are no seed scripts in the three database-backed service manifests; entrypoints run db push only. Register explicitly creates `{name,email,password:hashedPassword}`, and the auth schema defaults role to `USER`; supplying role in registration does not promote an account. Evidence: `ecommerce-microservices/auth-service/package.json:4-8`, `ecommerce-microservices/product-service/package.json:4-8`, `ecommerce-microservices/order-service/package.json:4-8`; each service's `entrypoint.sh:4-8`; `ecommerce-microservices/auth-service/src/controllers/authController.ts:35-45`, `ecommerce-microservices/auth-service/prisma/schema.prisma:10-20`.

It creates neither the user nor categories/products. This is the source-documented promotion method; it was not executed. A later bootstrap must register the user before promotion and login/refresh afterwards to mint an access token with the new role. Product/order authorization reads the role claim in that token, not live database state. Evidence: `ecommerce-microservices/README.md:208-210`, `ecommerce-microservices/auth-service/src/controllers/authController.ts:13-26,69-89,105-117`, `ecommerce-microservices/product-service/src/middlewares/auth.ts:16-34`, `ecommerce-microservices/order-service/src/middlewares/auth.ts:16-34`.

The existing API creation paths for categories and products both require admin; categories must exist before products because product creation supplies categoryId. No automatic catalog seed runs on startup. A bootstrap using the app API therefore needs `POST /categories` and `POST /products` with an admin token (direct database manipulation is a separate option, not an implemented catalog seed). No-image JSON products skip external Cloudinary uploads. The frontend admin page lists categories and creates/deletes products; it does not implement a category creation request. Evidence: `ecommerce-microservices/product-service/src/routes/productRoutes.ts:20-34,61-68`, `ecommerce-microservices/product-service/src/controllers/productController.ts:112-143`, `ecommerce-microservices/product-service/prisma/schema.prisma:27-28`, `ecommerce-microservices/frontend/src/app/admin/page.tsx:37-65`; service entrypoints/manifests cited above.

## 11. RabbitMQ management HTTP contract — official documentation, not target-source evidence

Verified 2026-10-11 using rabbitmq.com only. This section records the vendor's HTTP
contract, not a runtime observation of the target or an inference from its application code.

Read a single queue with `GET /api/queues/{vhost}/{name}`. Percent-encode each path segment:
the default vhost `/` becomes `%2F`, so this target's request is
`GET /api/queues/%2F/notifications`. HTTP Basic authentication uses a RabbitMQ username
and password. The successful JSON object identifies the queue with `name` and `vhost`;
200 plus matching identifiers establishes existence. A missing queue is reported as 404;
connection failures and authentication errors do not establish absence.
Documentation: [HTTP API reference](https://www.rabbitmq.com/docs/http-api-reference)
(Overview, GET /api/queues/{vhost}/{name}, and queue response-field sections).

Fields used by Phase 2:

| JSON field | Meaning / use |
|---|---|
| `name`, `vhost` | Confirm the requested queue identity. |
| `consumers` | Number of consumers; expect at least one. |
| `messages_ready` | Messages waiting for delivery; compare before/after checkout. |
| `messages` | Total queue messages, including deliveries awaiting acknowledgement; report for context. |

The API queue-field section incorporates `rabbitmqctl list_queues` fields; their definitions
are in the official [rabbitmqctl manual](https://www.rabbitmq.com/docs/man/rabbitmqctl.8#list_queues).
Missing metrics are unavailable evidence, not zero. RabbitMQ 3.13 emits statistics every
five seconds by default, so wait between observations:
[3.13 management statistics interval](https://www.rabbitmq.com/docs/3.13/management#statistics-interval).
The current API reference is version 4.3; the target declares a RabbitMQ 3 image. Compatibility
of these queue fields with the live image remains a human integration check.

**Target configuration facts (source, separate from the vendor contract):** the host management
port is `15672`; Compose sets `RABBITMQ_DEFAULT_USER=ecommerce` and the local sample password
`RABBITMQ_DEFAULT_PASS=ecommerce123` (`ecommerce-microservices/docker-compose.yml:49-64`,
already cited in section 1). Phase 2 defaults use those values, never the vendor's guest account.
Override them through `RABBITMQ_MANAGEMENT_URL`, `RABBITMQ_USER`, `RABBITMQ_PASSWORD` and
`RABBITMQ_VHOST` in ChaosPilot configuration when the live deployment differs. No runtime
credentials or `.env` contents were inspected.
